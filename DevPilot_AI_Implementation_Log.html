Plain-language primer

Written for someone brand new to MCP. Every term below is used in the entries further down — read this once, then the entries should read like plain engineering notes rather than jargon.

MCP Server

A small program that owns one capability — "talk to the filesystem", "talk to the terminal", "talk to GitHub" — and exposes a fixed menu of things it can do, called tools. It doesn't know or care who's calling it or why; it just answers requests. Ours so far is mcp_servers/filesystem/server.py — it only knows how to read files and directories, nothing else.

MCP Client

The piece of code that connects to a server, asks it "what can you do?", and then asks it to actually do one of those things. In a real AI assistant, the client sits between the LLM and every server — the LLM never talks to a server directly, it always goes through the client. Our lesson1_client.py and stage2_client.py are stand-ins for that piece, without an LLM wired in yet.

Tool

One specific action a server can perform — read_file, list_directory. In code it's just a normal Python function; what makes it an "MCP tool" is the @mcp.tool() decorator above it, which registers that function so the server can advertise it and the client can call it by name instead of by importing the function directly.

Tool schema

A machine-readable description of what arguments a tool needs, generated automatically from the function's Python type hints. For read_file(path: str) the schema says: one argument, named path, must be a string, and it's required. This is the part an LLM actually reads to figure out how to call a tool correctly — the human-readable description (the docstring) is context, the schema is the contract.

Tool discovery vs. tool invocation

Two separate steps, always in this order. Discovery is the client asking "what tools exist?" (list_tools()) and getting back names + descriptions + schemas, with nothing executed yet. Invocation is the client actually calling one of those tools by name with real arguments (call_tool("read_file", {"path": "..."})) and getting a result back. Discovery is how an LLM learns its options; invocation is it acting on one.

content vs. structured_content

Every tool call returns both. content is a list of display-oriented blocks (mostly TextContent, i.e. plain text) — it's what you'd show a human or feed back into an LLM's context. structured_content is the tool's actual typed return value, still shaped like real data (a list, a dict). They are not always interchangeable — Entry 6 below hit this directly: a tool returning list[str] got split into several separate content text blocks (one per item) with the full list only available in structured_content, while a tool returning dict put everything into one content block as a JSON string and left structured_content as None. Assuming "the answer is always in content[0].text" is a real, easy-to-make bug — it silently truncates list-shaped results instead of erroring, which is worse than crashing.

Sandboxing / workspace root

Because a Filesystem MCP server can read (and later write) real files on disk, every tool that takes a path argument resolves that path and checks it's still inside one fixed folder (WORKSPACE_ROOT) before doing anything with it. Without this, a tool call like read_file("../../../../etc/passwd") would just work — the server has no other reason to refuse it. This check is not optional hardening added later; it's load-bearing from the first tool onward.

Entry 3 — Filesystem MCP server: read_file tool

2026-08-09 · Stage 1 · Status: done
Approach

Build the smallest possible MCP server: one tool, read_file, that reads a text file's contents. Per the standing security decision (logged 2026-08-09 in the learning log), the workspace-root sandbox is built in from this very first tool, not added later — every path is resolved and checked against a fixed WORKSPACE_ROOT before the file is touched.

Will do: read files inside the project folder.
Won't do: read anything outside the project folder (e.g. ../../secrets.txt, absolute paths elsewhere on disk, or symlinks that resolve outside the root) — those raise ValueError instead of returning content.

Implementation

File: mcp_servers/filesystem/server.py

from pathlib import Path
from mcp.server import MCPServer

WORKSPACE_ROOT = Path(__file__).resolve().parents[2]

mcp = MCPServer("DevPilot Filesystem")

@mcp.tool()
def read_file(path: str) -> str:
    """Read a text file's contents from within the DevPilot workspace."""
    target = (WORKSPACE_ROOT / path).resolve()

    if target != WORKSPACE_ROOT and WORKSPACE_ROOT not in target.parents:
        raise ValueError(f"Access denied: '{path}' is outside the workspace root.")

    if not target.is_file():
        raise FileNotFoundError(f"No such file: '{path}'")

    return target.read_text(encoding="utf-8")

if __name__ == "__main__":
    mcp.run()

Line-by-line reasoning:

  • WORKSPACE_ROOT is computed from the server file's own location (2 parents up), not from the current working directory — so the sandbox boundary doesn't shift depending on where the process is launched from.
  • (WORKSPACE_ROOT / path).resolve() collapses any .. segments before the check runs — this is what makes the traversal check actually work, rather than comparing against an un-resolved, spoofable path string.
  • The check uses target.parents (all ancestor directories) rather than a string prefix check like str(target).startswith(str(WORKSPACE_ROOT)) — a prefix check is a classic sandbox bug, since /workspace-evil starts with the string /workspace but is a sibling directory, not a child.
Outcome

Verified in Entry 5 below.

Entry 6 — Stage 2: multiple Filesystem tools

2026-08-09 · Stage 2 · Status: implemented and tested
Approach

Concept being taught: tool discovery and tool selection when a server exposes more than one tool. In Stage 1 list_tools() returned an array with exactly one entry, so "discovery" was trivial. The interesting part of MCP — the LLM reading several schemas and picking the right one for the request — only shows up once there's a choice to make.

What did the request under the hood, resolved above: list_tools() sends a single tools/list request; the server returns one Tool entry (name + description + auto-generated JSON-Schema) per @mcp.tool()-decorated function currently registered on it. Adding tools below means that same single request will come back with 4 entries instead of 1 — nothing about the discovery mechanism changes, only what's in the array.

Planned tools (per # DevPilot AI – MCP Learning & Build Ins.md §6, "Initial tools"), added to the existing mcp_servers/filesystem/server.py:

ToolSignatureBehavior
list_directory(path: str) -> list[str]Names of entries directly inside path.
get_file_info(path: str) -> dictSize, is_dir, last-modified time for one path.
search_files(query: str) -> list[str]Recursively find filenames containing query (substring match). File-content semantic/keyword search is explicitly out of scope here — that's the "Workspace Search" capability in the project design doc, scheduled for Phase 3, not Stage 2.

Rather than copy-pasting that check four times, the plan is to extract it into one shared helper, _resolve_within_workspace(path) -> Path, that all four tools call — this is a straight duplication removal, not a speculative abstraction (the exact same check would otherwise appear four times in one file).

Will do: read-only inspection of files/directories inside the workspace, same as Stage 1.
Won't do: no write/create/delete tools yet (those are explicitly flagged as needing approval-gating in the build instructions, §6, and that gating mechanism doesn't exist yet) — still read-only for the whole Filesystem MCP server at this stage.

How this will be tested once implemented: extend the Stage 1 client to call list_tools() again and print all 4 tool names + schemas (proving discovery scales), then call each new tool once on a real path/file in this repo, plus one traversal attempt against search_files to confirm the shared sandbox helper is actually wired into the new tools and not just the old one.

Implementation

One deliberate deviation from the approach above: the original plan wrote search_files(query: str) -> list[str] with no path parameter, searching the whole workspace every time. While implementing it became clear that would leave search_files as the one tool with nothing to sandbox — no path input means no traversal is even possible, which would make the planned traversal test meaningless for this tool. Fixed by giving it an optional path: str = "." parameter to scope the search, which (a) is more realistic anyway — "search under src/" is a normal request — and (b) means all four tools now genuinely share the same sandbox helper, and all four can be traversal-tested the same way. This is exactly the kind of thing the Approach step exists to catch before it's a surprise, but this particular gap only became visible once the code was actually being written — recorded here rather than silently changed.

File: mcp_servers/filesystem/server.py — added a private helper and three new @mcp.tool()-decorated functions:

def _resolve_within_workspace(path: str) -> Path:
    """Resolve `path` against the workspace root and reject anything outside it."""
    target = (WORKSPACE_ROOT / path).resolve()
    if target != WORKSPACE_ROOT and WORKSPACE_ROOT not in target.parents:
        raise ValueError(f"Access denied: '{path}' is outside the workspace root.")
    return target

@mcp.tool()
def list_directory(path: str = ".") -> list[str]:
    """List the names of entries directly inside a directory in the workspace."""
    target = _resolve_within_workspace(path)
    if not target.is_dir():
        raise NotADirectoryError(f"No such directory: '{path}'")
    return sorted(entry.name for entry in target.iterdir())

@mcp.tool()
def get_file_info(path: str) -> dict:
    """Return size, type, and last-modified time for a path in the workspace."""
    target = _resolve_within_workspace(path)
    if not target.exists():
        raise FileNotFoundError(f"No such path: '{path}'")
    stat = target.stat()
    return {
        "path": path,
        "is_dir": target.is_dir(),
        "size_bytes": stat.st_size,
        "modified": datetime.fromtimestamp(stat.st_mtime, tz=timezone.utc).isoformat(),
    }

@mcp.tool()
def search_files(query: str, path: str = ".") -> list[str]:
    """Recursively search a directory in the workspace for filenames containing `query`."""
    base = _resolve_within_workspace(path)
    if not base.is_dir():
        raise NotADirectoryError(f"No such directory: '{path}'")
    query_lower = query.lower()
    matches: list[str] = []
    for entry in base.rglob("*"):
        if not entry.is_file():
            continue
        if any(part in _EXCLUDED_DIR_NAMES for part in entry.relative_to(WORKSPACE_ROOT).parts):
            continue
        if query_lower in entry.name.lower():
            matches.append(str(entry.relative_to(WORKSPACE_ROOT)))
    return sorted(matches)

Why read_file itself was also touched: its inline sandbox check (the four lines that used to sit directly inside the function) was replaced with a call to the new _resolve_within_workspace() helper. The behavior is identical — same check, same error message — only where the check lives changed. This matters for the lesson: the four tools are not four independent implementations of "is this path safe", they are four callers of one implementation. If that one implementation ever needs a fix (say, to also reject symlinks that escape the root), it gets fixed in exactly one place and all four tools inherit the fix automatically.

Also added _EXCLUDED_DIR_NAMES = {".venv", "__pycache__", ".git"}, checked inside search_files only. Without it, searching this repo would recurse into .venv and return hundreds of installed-package files having nothing to do with the project — a usability fix, not a security one (nothing in .venv is outside the sandbox, it's just noise).

Client: created a new file, mcp_client/stage2_client.py, rather than editing lesson1_client.py — the Stage 1 file is left alone as a clean, already-verified "smallest example" you can go back to, while the new file exercises the full four-tool surface.

Entry 7 — Stage 3: Terminal MCP

2026-08-10 · Stage 3 · Status: implemented and tested
Approach

Concept being taught: this is the first server where a "wrong" result and a "dangerous" result are different problems that need different handling. Reading a file either works or fails cleanly. Running a command can succeed, fail on purpose (a genuinely failing test suite — exit_code=1 is correct, useful information, not a bug), fail by accident (typo, missing dependency), or be something that should never run at all (rm -rf). Stage 3 is about building the machinery to tell those apart: Tool Permissions (what's even allowed to run) and Error Handling (a non-zero exit code is not an MCP error — it's a normal, successful tool call that happens to report failure).

Planned tool — one tool, not two. The build-instructions file's own Terminal MCP section lists execute_command + get_command_output as separate tools, which implies an async pattern: start a command, then poll for its output later. That's the right shape for something like a Docker build that can run for minutes — but we already decided (learning log, Approach & Decisions table) that async/job-queue execution is a Phase 3/4 concern, introduced when Docker MCP actually needs it. Building that machinery now, before anything requires it, would be exactly the "excessive abstraction" the project's own §28 says to avoid. So Stage 3 ships one synchronous tool:

execute_command(command: str, args: list[str] | None = None, timeout_seconds: int = 30) -> dict
    # returns {"stdout": str, "stderr": str, "exit_code": int}

Security plan — four independent layers, each closing off a different way this tool could be misused:

LayerMechanismCloses off
Allow-listFixed set of permitted binaries: python, pip, pytest, npm, git. Anything else is rejected before a process is ever spawned.rm, sudo, arbitrary binaries.
No shellsubprocess.run([command, *args], shell=False) — command and each argument passed as a separate list item, never assembled into one shell string.Shell metacharacters (;, &&, |, backticks) simply have no special meaning — there's no shell parsing them, so there's nothing to "block". This is a refinement over the original plan (learning log Entry) of pattern-matching to reject dangerous characters — avoiding the shell entirely is simpler and strictly safer than trying to blocklist characters in a string.
Fixed working directoryEvery command runs with cwd=WORKSPACE_ROOT, hardcoded — no cwd parameter exposed to the caller at all.Same class of problem the Filesystem sandbox solves, applied here by simply not accepting a path input, rather than validating one.
Bounded timeouttimeout_seconds param, default 30, hard-capped at 120 server-side regardless of what's requested.A hung/runaway process blocking the whole synchronous call indefinitely.

Explicitly not built yet: the human-approval workflow ("AI wants to run docker rm ... — Allow / Reject") is its own later stage (Stage 8 in the build-instructions file). It isn't needed yet because the allow-list already prevents anything destructive from running — there's nothing dangerous left to approve. docker is deliberately left off the allow-list too, even though the build-instructions example list includes it — Docker gets its own dedicated MCP server later in the architecture, so letting Terminal MCP also shell out to arbitrary docker subcommands would just be two servers with overlapping, harder-to-reason-about power.

Will do: run one allow-listed command with arguments, inside the workspace, with a bounded timeout, and report back exit code + stdout + stderr regardless of whether the command itself succeeded.
Won't do: run anything not on the allow-list, run with a different working directory, run indefinitely, or ask for human approval (nothing on the allow-list needs it yet).

How this will be tested once implemented: (1) a benign allow-listed command (e.g. git --version) to confirm the happy path and that exit_code == 0; (2) a command that runs but is meant to fail (e.g. python -c "import sys; sys.exit(1)") to prove a non-zero exit code comes back as a normal result, not a thrown error; (3) a disallowed command (e.g. rm) to confirm it's rejected before execution; (4) a deliberately slow command against a short timeout_seconds to confirm the timeout actually fires.

Implementation

Files: mcp_servers/terminal/server.py (new server, mirrors the same shape as the Filesystem server — module-level constants, MCPServer("DevPilot Terminal"), one @mcp.tool() function) and mcp_client/stage3_client.py (new test client, following the Stage 2 pattern of a shared _print_result() helper).

ALLOWED_COMMANDS = {"python", "pip", "pytest", "npm", "git"}
MAX_TIMEOUT_SECONDS = 120

mcp = MCPServer("DevPilot Terminal")

@mcp.tool()
def execute_command(
    command: str, args: list[str] | None = None, timeout_seconds: int = 30
) -> dict:
    """Run an allow-listed command inside the workspace and report its result."""
    if command not in ALLOWED_COMMANDS:
        raise ValueError(
            f"Command '{command}' is not allowed. Allowed commands: {sorted(ALLOWED_COMMANDS)}"
        )

    bounded_timeout = min(timeout_seconds, MAX_TIMEOUT_SECONDS)
    argv = [command, *(args or [])]

    try:
        completed = subprocess.run(
            argv,
            cwd=WORKSPACE_ROOT,
            capture_output=True,
            text=True,
            timeout=bounded_timeout,
            shell=False,
        )
    except subprocess.TimeoutExpired as exc:
        raise TimeoutError(
            f"Command '{' '.join(argv)}' timed out after {bounded_timeout}s"
        ) from exc
    except FileNotFoundError as exc:
        raise FileNotFoundError(
            f"'{command}' is allow-listed but not installed on this system."
        ) from exc

    return {"stdout": completed.stdout, "stderr": completed.stderr, "exit_code": completed.returncode}

Line-by-line reasoning for the parts that aren't self-explanatory:

  • The allow-list check happens before anything else — including before bounded_timeout is even computed. A disallowed command never reaches subprocess.run at all; there's no code path where an unapproved binary gets spawned and then stopped partway through.
  • bounded_timeout = min(timeout_seconds, MAX_TIMEOUT_SECONDS) — the caller (eventually an LLM) can request a shorter timeout, but can never request a longer one than the server allows, no matter what argument it passes.
  • Two different exceptions map to two different real-world causes that look similar but aren't: subprocess.TimeoutExpired (the process was still running when time ran out — the command itself might be fine, it just took too long) is re-raised as TimeoutError; FileNotFoundError (the binary is allow-listed but genuinely not installed on this machine — e.g. calling npm on a machine without Node) gets a clearer message than Python's default, which would otherwise read like a generic OS error.
  • capture_output=True, text=True captures stdout/stderr as decoded strings (not bytes) so they can go straight into the tool's JSON-shaped result without extra decoding.

GITHUB_API_BASE = "https://api.github.com"
REQUEST_TIMEOUT_SECONDS = 10

mcp = MCPServer("DevPilot GitHub")

def _auth_headers() -> dict:
    headers = {"Accept": "application/vnd.github+json"}
    token = os.environ.get("GITHUB_TOKEN")
    if token:
        headers["Authorization"] = f"Bearer {token}"
    return headers

@mcp.tool()
def get_repository(owner: str, repo: str) -> dict:
    """Fetch curated public metadata for a GitHub repository."""
    url = f"{GITHUB_API_BASE}/repos/{owner}/{repo}"

    try:
        with httpx2.Client(timeout=REQUEST_TIMEOUT_SECONDS) as client:
            response = client.get(url, headers=_auth_headers())
    except httpx2.RequestError as exc:
        raise ConnectionError(f"Could not reach GitHub API: {exc}") from exc

    if response.status_code == 404:
        raise ValueError(f"Repository '{owner}/{repo}' not found.")
    if response.status_code == 403:
        raise PermissionError(
            "GitHub API request forbidden or rate-limited. "
            "Set the GITHUB_TOKEN environment variable for higher rate limits."
        )
    if response.status_code != 200:
        raise RuntimeError(f"GitHub API returned unexpected status {response.status_code}.")

    data = response.json()
    return {
        "name": data["name"], "full_name": data["full_name"],
        "description": data["description"], "default_branch": data["default_branch"],
        "stargazers_count": data["stargazers_count"], "open_issues_count": data["open_issues_count"],
        "language": data["language"], "html_url": data["html_url"],
    }

Notes on choices that aren't obvious from the code alone:

  • _auth_headers() is the only place GITHUB_TOKEN is ever read. It builds a headers dict that goes straight into the outgoing HTTP request and is never returned, logged, or otherwise exposed — the token flows from environment variable to HTTP header and nowhere else.
  • Status-code checks happen before response.json() is ever called — a 404 or 403 response from GitHub still has a JSON body, but it's GitHub's own error shape, not repository data, so parsing it as if it were a repository would be wrong even if it wouldn't crash.
  • The return dict lists exactly 8 fields, chosen by hand, out of the ~115 fields GitHub's API actually returns for a repository — this is the "curate, don't pass through raw upstream JSON" decision from the Approach, made concrete.

Approach

Security plan — the new concern here is SSRF, not sandboxing. Filesystem/Terminal each had one clear boundary (workspace root, allow-list). fetch_page is different: fetching arbitrary external URLs is the point, so there's no workspace-style boundary to apply. The real risk is a tool that fetches "any URL" being pointed at something that isn't really documentation — http://localhost/admin, http://169.254.169.254/ (the cloud metadata endpoint many SSRF exploits target), or an internal 10.x/192.168.x address. Plan: reject before fetching if the URL's scheme isn't http/https, or if the resolved host is localhost, a loopback address, or a private/link-local IP range. This is a real production concern (flagged generically in DevPilot_AI_MCP_Project_Design.md's security section) made concrete for the first time, the same way Stage 1 made "sandboxing" concrete for Filesystem.

Being upfront about a real limitation: search_web scrapes a public HTML page with no official API contract — unlike GitHub MCP's REST API, DuckDuckGo can change this markup at any time with no notice or versioning, which would silently break parsing. This is a deliberate, documented trade-off for a zero-cost, no-API-key learning project, not a production choice — a real deployment would swap this for a paid search API (Brave Search, Bing) behind the exact same search_web(query) -> list[dict] signature. The tool's interface is designed to survive that swap even though today's implementation is a stopgap.

The real URL is pulled out of the DuckDuckGo redirect link by _extract_real_url():

def _extract_real_url(redirect_href: str | None) -> str:
    """DuckDuckGo's result links wrap the real URL in a `uddg` query param."""
    if not redirect_href:
        return ""
    absolute = redirect_href if redirect_href.startswith("http") else f"https:{redirect_href}"
    query = parse_qs(urlparse(absolute).query)
    return unquote(query.get("uddg", [""])[0])

The if redirect_href.startswith("http") else f"https:{redirect_href}" line exists because the real markup has protocol-relative links (//duckduckgo.com/l/?uddg=..., no scheme) — urlparse can't extract query params correctly from a schemeless URL, so a scheme is prepended first, purely so parsing works; it's discarded immediately after.

_reject_unsafe_url() is the SSRF guard, called as the very first line of fetch_page — before any network request:

def _reject_unsafe_url(url: str) -> None:
    parsed = urlparse(url)
    if parsed.scheme not in ("http", "https"):
        raise ValueError(f"Refusing to fetch '{url}': only http/https URLs are allowed.")
    hostname = (parsed.hostname or "").lower()
    if hostname in ("localhost",):
        raise ValueError(f"Refusing to fetch '{url}': internal host is not allowed.")
    resolved_ip = socket.gethostbyname(hostname)
    ip = ipaddress.ip_address(resolved_ip)
    if ip.is_private or ip.is_loopback or ip.is_link_local or ip.is_reserved:
        raise ValueError(f"Refusing to fetch '{url}': resolves to a private/internal address ({resolved_ip}).")

localhost is checked by name explicitly, separately from the IP check, because it's a hostname, not an IP literal — the IP check only runs after DNS resolution, so localhost needs its own early rejection rather than relying on it resolving to 127.0.0.1 (which it usually does, but "usually" isn't a security boundary).

Known limitation, noted rather than solved: the hostname is resolved once for the safety check, and then httpx2 resolves it again when it actually connects. A DNS response could theoretically differ between those two lookups (DNS rebinding) — a fully hardened version would resolve once and connect to that pinned IP directly. Not fixed here; this is a Stage 5 learning example, not a hardened production tool, and the gap is written down rather than silently left implicit.

def _readonly_connection() -> sqlite3.Connection:
    """The real defense: a connection that structurally cannot write."""
    conn = sqlite3.connect(f"file:{DB_PATH}?mode=ro", uri=True, timeout=5)
    conn.row_factory = sqlite3.Row
    return conn

@mcp.tool()
def execute_read_query(query: str) -> list[dict]:
    """Run a read-only SQL query against the demo database, capped at 500 rows."""
    stripped = query.strip().lower()
    if not stripped.startswith(_READ_PREFIXES):
        raise ValueError(
            "Only SELECT/WITH queries are allowed. "
            f"Got a statement starting with: '{query.strip()[:20]}'"
        )
    conn = _readonly_connection()
    try:
        cursor = conn.execute(query)
        rows = cursor.fetchmany(MAX_ROWS)
        return [dict(row) for row in rows]
    except sqlite3.OperationalError as exc:
        raise ValueError(f"Query failed: {exc}") from exc
    finally:
        conn.close()

One detail worth calling out in describe_table: it interpolates the table name directly into a PRAGMA table_info(...) string, which would normally be a textbook SQL-injection shape. It's safe here specifically because table is checked against _existing_tables(conn) — the real list of tables from sqlite_master — before the interpolation happens. PRAGMA statements don't support SQLite's normal ? parameter binding for identifiers (only for values), so "validate against a known-good set, then interpolate" is the correct pattern here, not an oversight — parameter binding literally isn't an option for this particular statement.

Entry 12 — Stage 8: Approval System

2026-08-10 · Stage 8 · Status: implemented and tested — the most eventful stage so far
Approach

Concept being taught: human-in-the-loop — a tool pausing mid-execution to ask the connected human a question, then resuming based on the answer. This is a different shape of safety mechanism from everything built so far. Every prior gate (sandboxing, allow-listing, SSRF checks, read-only connections) is the server deciding autonomously, before or during a call, with no human involved. Approval is the first mechanism where the human is the gate — the server can't decide by itself at all, it has to stop and ask.

Verification performed before planning further (same discipline as every stage so far, but deeper this time — this turned out to be the least-obvious API surface encountered yet). MCP has a native protocol feature for exactly this, called elicitation — not something to hand-roll with a custom approval queue. Traced the real implementation across four files in the SDK source (not guessed):

  • A tool function can declare a parameter type-hinted ctx: Context; the SDK auto-injects the current request's Context object into it at call time, and — importantly — this parameter is excluded from the tool's public JSON schema. Confirmed in tools/base.py: find_context_parameter(fn) detects it, then pass_directly[self.context_kwarg] = context supplies it outside the normal validated-arguments path.
  • Inside the tool, await ctx.elicit(message: str, schema: type[BaseModel]) -> ElicitationResult sends the elicitation request. Confirmed signature in context.py.
  • ElicitationResult isn't one class with an action string to compare — it's a union of three real types, confirmed in mcp/server/elicitation.py: 
    class AcceptedElicitation(BaseModel, Generic[T]):
    action: Literal["accept"] = "accept"
    data: T                          # only present when accepted

class DeclinedElicitation(BaseModel):
    action: Literal["decline"] = "decline"

class CancelledElicitation(BaseModel):
    action: Literal["cancel"] = "cancel"
    The documented usage pattern is isinstance(outcome, AcceptedElicitation), not string comparison on .action.
  • Critical finding for testing: the client side must supply an elicitation_callback matching a specific Protocol (confirmed in client/session.py). Without one, the SDK's own default handler runs: 
    async def _default_elicitation_callback(context, params):
    return types.ErrorData(code=types.INVALID_REQUEST, message="Elicitation not supported")
    This means every prior test client (lesson1_client.py through stage6_client.py) would make write_file fail-safe by default — approval is opt-in on the tool side but the absence of a callback doesn't silently allow anything, it silently refuses everything. That fail-safe default is worth testing directly, not just asserted.

Not yet verified, deferred to implementation time: the exact field names on types.ElicitResult / types.ElicitRequestParams that a custom callback needs to construct/read — the source file wasn't reachable at the path tried. This will be confirmed empirically while writing the callback (same "verify against the real error, not a guess" approach that caught the two real bugs in Entry 6), rather than blocking the whole plan on one more fetch.

What gets gated: a new tool, write_file(path, content), added to the existing Filesystem MCP server — the natural first candidate, since the build-instructions file has said since §6 that file-modification tools "must require explicit user approval," and every write-capable operation across all 6 servers so far has explicitly deferred to "whenever Stage 8 exists." This is that moment, for exactly one tool — proving the mechanism end-to-end matters more than rolling it out everywhere at once.

class WriteApproval(BaseModel):
    pass  # no extra data needed -- the accept/decline/cancel action IS the answer

@mcp.tool()
async def write_file(path: str, content: str, ctx: Context) -> str:
    target = _resolve_within_workspace(path)   # existing Stage 1/2 sandbox check, unchanged

    outcome = await ctx.elicit(
        message=f"DevPilot wants to write {len(content)} characters to '{path}'. Approve?",

    if not isinstance(outcome, AcceptedElicitation):

Two things worth flagging about this specific design: the existing workspace-root sandbox check still runs first, before the human is ever asked anything — there's no reason to interrupt a human to approve a write that was going to be rejected anyway. And this is the first async def tool in the codebase (every prior tool has been a plain synchronous function) — required because ctx.elicit() is itself an await-able call.

Will do: gate exactly one destructive operation (write_file) behind real human approval via MCP's native elicitation mechanism, layered on top of the existing sandbox check, not replacing it.
Won't do: extend approval to other servers' hypothetical write operations yet (Terminal already refuses via allow-list rather than needing approval; GitHub/Browser/Database remain fully read-only) — one gated tool, proven end-to-end, is the right scope for this stage.

How this will be tested once implemented, using a custom elicitation_callback in the test client that can be scripted per call: (1) approve path — callback accepts, confirm the file is actually written with the right content; (2) decline path — callback declines, confirm a clean PermissionError and that the file was not created or modified; (3) fail-safe path — call write_file through a client with no elicitation_callback registered at all, confirm it refuses by default rather than silently writing; (4) confirm the sandbox still runs first — a ../ traversal attempt should be rejected without ever triggering an elicitation prompt.

Implementation

This stage did not go as planned, in the most useful way possible — three separate real problems surfaced while actually running the code, each one a genuine gap between "what the source code implies" and "what actually happens end-to-end." Documenting the journey, not just the final state, because each snag is a real lesson.

Snag 1 — the in-memory client can't do this at all. The very first attempt used the same Client(mcp) in-memory pattern every stage since Entry 4 has used. It failed immediately:

mcp.shared.exceptions.NoBackChannelError: Cannot send 'elicitation/create':
this transport context has no back-channel for server-initiated requests.

This is the real reason Entry 4 hedged: elicitation requires the server to send a request to the client mid-call and wait for a reply — a fundamentally bidirectional exchange. The in-memory shortcut is a direct function call dressed up as a client/server relationship; it has no channel for the server to initiate anything. Fix: switched to the real transport Entry 4 deferred — StdioServerParameters + stdio_client + ClientSession, spawning the Filesystem server as an actual subprocess. Snag 2 — the exact elicitation payload shapes weren't guessable, so they were probed. Rather than guess at ElicitResult's fields, a throwaway callback printed the real request/result shapes:

params type: ElicitRequestFormParams
params: {'meta': {}, 'mode': 'form', 'message': "DevPilot wants to write 2 characters to 'probe_test.txt'. Approve?",

And building a valid response requires types.ElicitResult(action="accept", content={}) or types.ElicitResult(action="decline") — not the server-side AcceptedElicitation/DeclinedElicitation classes from the Approach, which are a different, server-only representation of the same concept.

Snag 3 — the "no callback" failure mode isn't a normal tool error, and finding that out took two tries. First attempt used a plain except MCPError around the no-callback test call — it didn't catch anything, and the script crashed. Reason: anyio's structured concurrency wraps exceptions raised inside a TaskGroup (which stdio_client/ClientSession use internally) in an ExceptionGroup, not the bare exception. Python 3.11+'s except* syntax is what actually catches it. This is a second, independent confirmation of something worth generalizing: an error path with no elicitation callback registered isn't a normal CallToolResult(is_error=True) at all — it's a protocol-level MCPError, a structurally different failure than every other error this project has produced so far (allow-list rejections, sandbox rejections, SSRF rejections, declined approvals — all of those come back as ordinary tool results with is_error=True).

A Step dataclass (description, server, tool, args) represents one plan entry; PLAN is a plain list of three of them. _run_step() connects to whichever server the step names, calls the tool, and normalizes the result — including a detail not called out in the Approach: for dict-returning tools like execute_command, structured_content is None (the Stage 2/6 finding) and content[0].text is a JSON-encoded string, so it needs json.loads() to become a usable dict again before the report can pull stdout/ stderr out of it:

async def _run_step(step: Step) -> dict:
    server = SERVERS[step.server]
    async with Client(server) as client:
        result = await client.call_tool(step.tool, step.args)

    if result.is_error:
        return {"ok": False, "error": result.content[0].text}

    if result.structured_content is not None:
        value = result.structured_content
    else:
        raw = result.content[0].text
        try:
            value = json.loads(raw)          # dict-returning tools: JSON text -> dict
        except (json.JSONDecodeError, TypeError):
            value = raw                       # str-returning tools: already plain text

    return {"ok": True, "value": value}

run_plan() prints the plan up front, then executes each step in a loop, printing done. or FAILED: ... live and appending every outcome (success or failure) to the results list — nothing raises out of the loop on a single step's failure. _build_report() is the plain-formatting step, explicit in its own docstring that it is not an LLM summary.

    """Windows path -> WSL's auto-mounted /mnt/<drive>/... equivalent."""

    """Resolve the container's current bridge IP via `docker inspect`
    rather than hardcoding it -- container IPs aren't stable across restarts."""
    result = subprocess.run(
        ["wsl", "-d", "Ubuntu", "-e", "docker", "inspect", "-f",
         "{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}", OLLAMA_CONTAINER],
        capture_output=True, text=True, timeout=15,
    )
    ip = result.stdout.strip()
    if not ip:
        raise ConnectionError(f"Could not resolve an IP for container '{OLLAMA_CONTAINER}'...")
    return ip

def chat(message: str, timeout: int = DEFAULT_TIMEOUT_SECONDS) -> str:
    host = _resolve_ollama_host()
    url = f"http://{host}:{OLLAMA_PORT}/api/chat"
    payload = json.dumps({"model": OLLAMA_MODEL, "messages": [{"role": "user", "content": message}], "stream": False})
    result = subprocess.run(
        ["wsl", "-d", "Ubuntu", "-e", "curl", "-s", "-X", "POST", url,
         "-H", "Content-Type: application/json", "-d", "@-"],
        input=payload, capture_output=True, text=True, timeout=timeout,
    )
    if result.returncode != 0:
        raise ConnectionError(f"curl failed: {result.stderr.strip()}")
    data = json.loads(result.stdout)
    if "error" in data:
        raise RuntimeError(f"Ollama error: {data['error']}")
    return data["message"]["content"]

WORKSPACE_ROOT_ENV_VAR = "DEVPILOT_WORKSPACE_ROOT"
_PROJECT_ROOT = Path(__file__).resolve().parent.parent

def resolve_workspace_root() -> Path:
    override = os.environ.get(WORKSPACE_ROOT_ENV_VAR)
    if not override:
        return _PROJECT_ROOT
    root = Path(override).expanduser().resolve()
    if not root.is_dir():
        raise ValueError(
            f"{WORKSPACE_ROOT_ENV_VAR} is set to '{override}', "
            f"which is not a directory."
        )
    return root

The user wants DevPilot to work like Copilot or Claude Code: when the model wants to do something that changes state (write a file, commit, push, delete a branch, build/run/stop a container), it should ask a real question and wait for a real human answer before proceeding — not silently skip the tool, which is what Entry 23 shipped. That's a materially different, bigger piece than anything so far, and it's worth being explicit about why before writing code.

Why "just call ctx.elicit() from the agent loop" doesn't work over HTTP. Every prior elicitation test (Entry 12, Stage 8) ran in one continuous Python process — the client made a call, blocked, a human answered synchronously in the same terminal, done. The live app is not that: POST /ask is one HTTP request/response cycle. If the agent loop tried to block waiting for approval inside that handler, the request would just sit open with no way for the browser to show a prompt and send an answer back into the *same* paused call — HTTP requests don't work that way. So this needs actual pause/resume architecture, not a bigger version of Stage 8's callback.

Design, chosen piece by piece rather than assumed:

  • Sessions. A new in-memory backend/sessions.py store, one entry per conversation, holding status (running / awaiting_approval / done / error), the pending tool name+arguments+elicitation message when paused, and the final result once done.
  • Background execution. POST /ask starts the agent loop as a background asyncio task and returns a session_id immediately — it does not wait for the loop to finish, because the loop might pause partway through.
  • How the frontend notices a pause — polling, user-confirmed over Server-Sent Events. Simpler to build and debug than a new transport this project hasn't used yet, at the cost of a ~2s delay before a pending prompt appears. GET /session/{id} reports current status; when awaiting_approval, it includes the tool name, arguments, and the exact message the server's ctx.elicit() call passed.
  • Resuming — a real answer, not a fake one. POST /session/{id}/approve (body: approved: bool) resolves an asyncio.Future that the paused elicitation callback is genuinely awaiting. The callback then returns types.ElicitResult(action="accept", content={}) or action="decline" straight to the MCP server, exactly the shape confirmed live in Stage 8's stage8_client.py — so the gate is still enforced server-side, not faked by the client skipping the call. This matters: it would be easy to build a version where the backend just decides "approved, so call the tool directly," bypassing ctx.elicit() entirely — that would quietly undermine the same "mechanism over pattern-matching" principle the sandbox/allow-list/read-only-connection decisions were built on.
  • Gated tools rejoin the model's tool list. Entry 23's EXCLUDED_TOOLS hid these 7 tools from the model entirely, so it could never choose to call them. For real human-in-the-loop to mean anything, the model has to be able to propose the action — renamed to GATED_TOOLS, now used only to decide how a call is routed (through a real stdio session with an elicitation callback) rather than whether it's visible at all.
  • Per-call subprocess, not persistent. Each gated call opens its own stdio_client connection to the owning server (Filesystem/Docker/Git) via forwarded_env() (Entry 22), same pattern as stage8_client.py/git_client.py, rather than keeping long-lived subprocess connections alive across the whole session — simpler lifecycle, and these calls are already rare relative to read-only ones.

Will do: session store, background task execution, polling status endpoint, approve/decline endpoint, real stdio + elicitation-callback routing for all 7 gated tools (the 6 from Entry 23 plus write_file, now that the real mechanism exists — no reason to leave it on the old excluded path), a frontend approval prompt (tool name, arguments, the server's own message, Approve/Decline buttons), tested with one real approve and one real decline run, end-to-end through the browser.
Won't do: persisting sessions to disk (in-memory is fine — losing pending approvals on a backend restart is an acceptable loss for a local dev tool, not a production service); concurrent multiple-approvals-at-once (the loop only ever has one tool call in flight, so one pending slot per session is sufficient); Server-Sent Events (explicitly deferred per the user's own choice above).

Entry 56 — A Real Bug Inside trl Itself: the Default Chunked Loss Crashes

2026-08-28 · Real Kaggle GPU session, bf16-capable, both Entry 55 fixes confirmed working live · Status: fixed and verified against the real installed trl source; not yet re-confirmed end-to-end

Entry 57 — Premature-EOS Collapse: Five Hypotheses Ruled Out, One Real Fix

2026-08-28 · Real Kaggle training run completed cleanly; raw-output investigation found a deeper problem · Status: learning-rate/warmup fix applied and verified; not yet re-confirmed end-to-end
Approach

debug_predictions.py showed something new: not the Plan-mode-shaped refusal text seen before Entry 54's fix, but a single immediate <\|im_end\|> token — zero real content — on every tool_call example checked. Extending the tool to print raw token IDs (not just the special-token-stripped text a real predictor would see) confirmed it precisely: new tokens generated: 1 ids: [151645].

Checking whether this was universal or type-specific mattered for a real reason: ml/eval/metrics.py's task_completed and is_mode_violation both only check whether a tool was called, never whether real refusal TEXT was generated — a model producing nothing at all on a refusal-expected example scores identically to one producing a genuine explanation. A new --type refusal mode plus a full-set tally answered this with real numbers: 14/15 tool_call and 3/14 refusal held-out examples collapsed to immediate EOS. Not a clean split by type, but a large, real, quantified asymmetry — not something to guess past.

Implementation

Five real hypotheses, each checked and ruled out by direct verification — not by trial-and-error, before concluding this was a training-dynamics problem rather than one more fixable bug:

  1. Stale pre-fix dataset — ruled out; the user's own printed `train.jsonl` refusal examples showed the exact de-duplicated phrasing from Entry 54's fix.
  2. Label/prompt token misalignment — ruled out; verified locally, no GPU needed, that full_ids[:len(prompt_ids)] == prompt_ids held exactly for 5 real examples of each completion type (a subtler check than Concept #41's original STRING-prefix verification — this is the TOKEN-level prefix property, which BPE tokenizers don't always guarantee even when the string property holds).
  3. The loss_type="nll" change (Entry 56) — ruled out; reading trl's own compute_loss source directly found `"nll"` is a literal no-op (`if args.loss_type == "nll": pass # use the default loss`) — identical to whatever the original successful run's older trl version did implicitly.
  4. Precision — ruled out; `bf16=True` in both this run and the original successful one, confirmed via the printed `bf16 supported on this GPU: True` line.
  5. eos/pad token collision — ruled out; `generation_config.eos_token_id=[151645, 151643]` are two distinct, correctly-configured tokens (Qwen's own convention), and the model predicts `151645` — the CORRECT token type, just at the wrong position (first, instead of after real content).

What was left: a genuine, documented training- dynamics cause — `learning_rate=2e-4` with effectively 1 warmup step (3% of only 12 total steps for this project's real 57-example schedule, floored) is aggressive for a dataset this small and skewed (long masked prompts, short completions). Given three options, the user chose to lower the learning rate and raise warmup rather than grow the dataset or stop and document the finding as-is.

The fix itself needed its own verification, not just a round-number guess: `--learning-rate` (new CLI arg, default `1e-4`, was hardcoded `2e-4`) and `--warmup-ratio` (new CLI arg, default raised from a hardcoded `0.03`). Checked by direct arithmetic against this project's REAL 12-total-step schedule before committing to a value: 10% would have rounded right back down to the same 1-step warmup as the original 3% (`round(12*0.1)=1` vs `round(12*0.03)=0`, both floor to 1) — a "safe-sounding" fix that would have shipped as a no-op. `20%` (`round(12*0.2)=2`) is the smallest round ratio that actually changes anything for a schedule this short.

Outcome

The learning-rate/warmup fix verified against this project's own real dataset shape, not a generic example: new tests/test_train_qlora.py::test_default_warmup_ratio_is_twenty_percent_not_three asserts the exact real numbers (12 total steps → 2 warmup steps at the new default), so a regression back to a too-low default fails against real numbers, not an arbitrary case. Full suite: 149/149 passing.
