# DevPilot AI – Concepts, Approach & Implementation Log

This file is the running record for the DevPilot AI build. It exists so
that at any point — mid-project or months later — you (or I) can answer
"what have we actually covered, decided, and built" without re-reading
the whole conversation history.

It has three parts, updated in this order as we go:

1. **Concepts Learned** — MCP/AI concepts once they've been explained.
2. **Approach & Decisions** — architecture/process choices and *why*.
3. **Implementation Log** — what's actually been built and tested.

Nothing gets added to a section until it's actually happened — this is
a log, not a plan. The plan lives in `DevPilot_AI_MCP_Project_Design.md`.

# 1. Concepts Learned

| # | Concept | Status | Summary | DevPilot context |
|---|---------|--------|---------|-------------------|
| 1 | What is MCP | Introduced (2026-08-09) | A standard client-server protocol so any LLM app can talk to any tool/data source without bespoke glue code (N×M → N+M integrations). | Why DevPilot's 7 capabilities can be built as independent, swappable MCP servers instead of one tangled program. |
| 2 | MCP Client vs MCP Server | Introduced (2026-08-09) | Client lives in the app and talks to servers over a transport; each server exposes one capability's tools. | MCP Client = DevPilot's orchestration layer; Filesystem/Terminal/GitHub/etc. = separate servers. |
| 3 | Tool discovery | Introduced (2026-08-09) | Client asks a server "what tools do you have?"; server replies with name + description + JSON input schema per tool. | How the LLM learns what `filesystem.read_file` even is, before ever calling it. |
| 4 | Tool invocation | Introduced (2026-08-09) | Client sends a tool name + arguments to the server; server executes and returns a result, which flows back to the LLM as context. | The `read_file` → result → LLM step in every DevPilot workflow. |
| 5 | `content` vs `structured_content` | Learned the hard way (2026-08-09) | Every tool result carries both: `content` is display-oriented text blocks, `structured_content` is the real typed return value. A `list`-returning tool splits across N `content` blocks (full value only in `structured_content`); a `dict`-returning tool puts everything in one `content` block and leaves `structured_content` as `None`. Not interchangeable — assuming `content[0].text` is "the answer" silently truncates list results. | Caught via a real bug in `stage2_client.py`: `list_directory` appeared to return 1 entry instead of 8. |
| 6 | Tool schema (detail) | Reinforced (2026-08-09) | Auto-generated from type hints; the Python SDK object exposes it as `tool.input_schema` (snake_case), which differs from the wire protocol's `inputSchema` field name. | Caught via `AttributeError` in `stage2_client.py` — SDK attribute names and wire field names aren't guaranteed to match. |
| 7 | Tool Permissions (allow-listing) | Introduced (2026-08-10) | A tool doesn't have to accept everything it's technically capable of — `execute_command` rejects any binary not in a fixed allow-list *before* spawning a process, no execution attempt at all. | Terminal MCP's whole security model for Stage 3: `rm` is refused outright rather than run-and-caught. |
| 8 | Error Handling: tool failure vs. task failure | Introduced (2026-08-10) | A command that runs and exits non-zero is a **successful tool call** reporting a failure (`is_error` stays false) — not the same thing as the tool itself erroring (bad input, disallowed command, timeout), which *does* set `is_error`. | `execute_command` running `python -c "sys.exit(1)"` returned `exit_code: 1` as normal `structured_content`, no MCP-level error. |
| 9 | Multi-server architecture | Introduced (2026-08-10) | Independent MCP servers share no state and don't know about each other — GitHub MCP has no awareness of Filesystem/Terminal MCP. The client is the only thing that ever combines what several servers know. | First server (GitHub) with zero overlap in concerns with the other two — no sandboxing, no allow-list, entirely new failure modes (network/HTTP) instead. |
| 10 | Secrets handling in a tool | Introduced (2026-08-10) | A credential (`GITHUB_TOKEN`) is read only from the environment inside the tool, never accepted as a tool parameter and never returned in output — so there's no code path where the LLM could pass, see, or leak it. | `get_repository`'s schema exposes only `owner`/`repo`; confirmed via `list_tools()` that no token-shaped field exists. |
| 11 | External knowledge retrieval (vs. RAG) | Introduced (2026-08-10) | Grounding an LLM's answer in real external content doesn't require the full RAG pipeline (chunking/embeddings/vector DB) — "search, fetch, read the text" is a complete, useful capability on its own. RAG is a later, separate addition, not a prerequisite. | `search_web` + `fetch_page` give DevPilot real documentation lookup with zero retrieval infrastructure. |
| 12 | SSRF (Server-Side Request Forgery) | Introduced (2026-08-10) | A "fetch any URL" tool is a classic SSRF vector — it can be pointed at internal services (`localhost`, private IPs) or cloud metadata endpoints (`169.254.169.254`) that were never meant to be reachable this way. Guarding against it means checking both the hostname *and* the IP it resolves to, before fetching. | `fetch_page`'s `_reject_unsafe_url()`, tested against both a hostname (`localhost`) and an IP-literal (`169.254.169.254`) attack shape. |
| 13 | Mechanism over pattern-matching (structural defense) | Reinforced (2026-08-10) | Preferring a mechanism that makes the dangerous action *impossible* over one that tries to detect and block it after the fact. First seen in Stage 3 (`shell=False` — no shell means no metacharacters to blocklist); reinforced in Stage 6 with a genuinely independent test. | Opened SQLite in read-only mode (`file:...?mode=ro`); a raw write attempted *directly against that connection, bypassing the tool's own prefix check entirely*, still failed with `sqlite3.OperationalError: attempt to write a readonly database` — proving the engine-level guarantee, not just the string check in front of it. |
| 14 | Human-in-the-loop / MCP elicitation | Confirmed working end-to-end (2026-08-10) | A tool can pause *mid-execution* and ask the connected client/user a question via `ctx.elicit(message, schema)`, then resume based on `AcceptedElicitation`/`DeclinedElicitation`/`CancelledElicitation`. This is a fundamentally different safety mechanism from every prior gate — sandboxing/allow-listing/SSRF-checks/read-only-connections are the *server* deciding alone; elicitation makes the *human* the gate, and the server literally cannot decide by itself. | `write_file` on Filesystem MCP (Stage 8) — the first tool the server can't resolve on its own. Approve/decline paths both confirmed with independent `read_file` checks, not just trusting the write call's own report. |
| 15 | Fail-safe defaults | Confirmed (2026-08-10) | When no `elicitation_callback` is registered on the client, MCP's own default handler refuses the request rather than silently approving or hanging — absence of an approval mechanism means *nothing* gets approved, not everything. | Tested directly: a bare `ClientSession` with no callback made `write_file` fail, and a follow-up `read_file` confirmed no file was created — "fails safe" verified as "nothing written," not just "an error appeared." |
| 16 | Server-initiated requests need a real back-channel | Learned the hard way (2026-08-10) | The in-memory `Client(mcp)` shortcut (used since Stage 1) is a direct function call dressed as a client/server relationship — it has no channel for the *server* to send a request *to* the client mid-call. Elicitation needs exactly that. Any MCP capability requiring server→client requests (elicitation, sampling, roots) needs a real transport, full stop. | `NoBackChannelError` on the first Stage 8 attempt forced a switch to real `StdioServerParameters`/`stdio_client`/`ClientSession` — the first genuinely separate-process connection in the project, arrived at by necessity rather than by plan. Retroactively corrects the Entry 4 decision. |
| 17 | Protocol-level errors vs. tool-level errors | Learned the hard way (2026-08-10) | Not every failure comes back as `CallToolResult(is_error=True)`. A missing elicitation callback fails at the *protocol* level — `MCPError` raised straight out of `call_tool()` (wrapped in an `ExceptionGroup` by anyio's structured concurrency, needing Python 3.11+'s `except*` to catch) — structurally different from every other error this project has produced (allow-list/sandbox/SSRF rejections, declined approvals), which all surface as ordinary tool results. | First `except MCPError` attempt in `stage8_client.py` silently failed to catch anything; `except* MCPError` was needed. |
| 18 | Multi-server orchestration in one client | Confirmed working (2026-08-10) | Every client through Stage 8 connects to exactly one server. A planner/orchestrator is the first client that talks to *two* servers in the same script, in sequence, using each step's result independently of how the others turned out. This — not cleverness in choosing steps — is the real mechanical substance of "planning." | `planner.py` calling Terminal MCP twice and Filesystem MCP once in a single run, producing one combined report. |
| 19 | Plan generation vs. plan execution | Introduced (2026-08-10) | These are separable concerns: *execution* (run a sequence of tool calls across servers, pass results forward, tolerate individual failures) doesn't require an LLM at all; *generation* (turning a free-text request into that sequence) does. Proving execution first, with a fixed hand-written plan, isolates "MCP mechanics" from "LLM plumbing" instead of conflating them in one stage. | Stage 9 ships execution only; `PLAN` in `planner.py` is a hardcoded Python list, not LLM output. |
| 20 | Session vs. project memory (lifetime) | Confirmed working across 2 real processes (2026-08-10) | Session/conversation memory dies with the process; project memory persists across separate runs. The difference is only real if demonstrated across an actual process boundary, not just two calls inside one script. | `planner.py` run twice as genuinely separate OS processes: `ProjectMemory`'s `stages_completed` read back as 1 in run 2 (written by run 1) and became 2; every `SessionMemory.summary()` in both runs started from zero entries regardless. |
| 21 | Cross-environment execution (Windows host, WSL-bridged tool) | Introduced (2026-08-11) | An MCP server doesn't have to run its underlying capability in the same OS environment as the Python process hosting it — as long as there's a reliable bridge (here, `wsl.exe`) and a way to translate paths between the two environments' filesystems, the tool abstraction still holds. | Docker MCP's Windows Python process calls `docker` (which only exists in WSL) via `wsl -d Ubuntu -e docker ...`, with `_to_wsl_path()` converting the sandboxed Windows path into WSL's `/mnt/<drive>/...` mount for `build_image`. |
| 22 | Defense-in-depth vs. reachable gate | Introduced (2026-08-11) | Not every safety check sits on a path a caller can actually reach. Docker MCP's subcommand allow-list guards against a *future* tool that might expose a free subcommand parameter — none of today's six tools do, each hardcodes its own subcommand — so it's defense-in-depth, not the primary gate the way Terminal MCP's identical-looking allow-list is (where `command` genuinely is caller-controlled). | Had to be tested by importing `_run_docker()` directly, since no tool call could reach the rejection path through the public API. |
| 23 | Approval vs. underlying success are independent | Confirmed (2026-08-11) | "Was this approved?" and "did the approved action succeed?" are two separate questions. `git_commit`'s approve-path correctly reached real git execution and got a real git error (not a git repo) — proving the approval → execution wiring works, without needing the underlying operation to actually succeed. | `git_commit`, approved, in a folder with no `.git` — `AcceptedElicitation` was returned, `_run_git()` was genuinely called, and it failed for an honest, unrelated reason. |
| 24 | First LLM in the loop | Confirmed working (2026-08-11) | The actual "AI" in DevPilot AI — 6 servers, 26 tools, and a memory system were all built and tested before any of them had a model to sit under. A model with no project context honestly said "I don't know" rather than inventing a plausible-sounding answer, which is precisely the gap MCP tool access (Piece 2) exists to close. | `llm/demo.py` asking a local model to name an MCP server this project built — it correctly declined to guess. |
| 25 | Tool selection vs. answer synthesis are separate capabilities | Learned the hard way, twice (2026-08-11) | An LLM correctly discovering, choosing, and chaining the right tools across multiple servers does not guarantee it correctly synthesizes a final answer from everything it gathered. These are two different failure points and need testing separately. | Run 2 of the agent test: model called `read_file` (Filesystem) then `list_tables`/`describe_table` (Database) — genuine cross-server chaining, entirely correct — then wrote a final answer that silently dropped the dependency data it had already fetched. |
| 26 | A tool list is a real security/scope boundary, not just a convenience | Learned the hard way (2026-08-11) | "Which server object I import and pass to `list_tools()`" determines exactly which capabilities an LLM can reach — including ones never intended to be exposed. Importing a whole MCP server pulls in everything registered on it, approval-gated tools included, unless explicitly filtered. | `write_file` (Stage 8's approval-gated tool) appeared in the LLM's tool list on the first run despite the Approach explicitly scoping this piece to read-only tools — caught by testing, not by re-reading the plan. |
| 27 | System prompts as a coverage lever | Confirmed working (2026-08-11) | An explicit "check your answer covers every part of the question before finalizing" instruction in a system-role message fixed Entry 18's synthesis gap on the first re-run of the identical question — a prompting mitigation, not a structural guarantee, and reported as exactly that. | Same two-part question as Entry 18 Run 2: with the system prompt, the model gathered both facts in one turn and produced a complete, accurate two-part answer; without it, it had dropped one part twice. |
| 28 | HTTP surface doesn't change the underlying pipeline | Confirmed (2026-08-11) | Wrapping `llm/agent.py`'s `ask()` in a FastAPI endpoint and calling it over real HTTP produced the same correct behavior as calling it directly from a Python script — the MCP discovery/selection/execution/synthesis pipeline is transport-agnostic, as it should be, and this was verified rather than assumed. | `POST /ask` on a real running `uvicorn` server returned the correct answer about the demo database's tables, matching prior in-process test results. |
| 29 | Cached browser binaries can silently mismatch an npm package version | Learned the hard way (2026-08-11) | A `playwright` npm install doesn't guarantee the exact Chromium build it expects is already on disk, even when *a* cached build exists — the fresh install expected build 1234, the machine only had 1228 cached from something else. Verified by running it and reading the real error, not assumed compatible. | `browserType.launch: Executable doesn't exist at ...chromium_headless_shell-1234\...` on the first real browser-driven test of the frontend; fixed with `npx playwright install chromium`. |
| 30 | A capability's own security boundary isn't real if a different tool can reach the same action unguarded | Learned the hard way, via deliberate gap audit (2026-08-23) | Approval gates are per-*action*, not per-*server* — if two different tools can both cause the same real-world effect (here: run `git commit`/`git push`), gating only one of them is not a security boundary at all, it's a coin flip on which tool the model happens to pick. Git MCP's commit/push/branch-delete gates (Entry 16) had been correct and well-tested in isolation the whole time; the gap was Terminal MCP allowing the *same underlying commands* through a completely different, ungated path. | Terminal MCP's `execute_command` allow-listed bare `git`, so `execute_command(command="git", args=["push","--force"])` ran with zero approval — fully bypassing Git MCP's dedicated gates. Found by deliberately auditing every allow-listed command against "what else, in this whole codebase, could cause this same effect?" rather than reviewing each server in isolation. |
| 31 | Reusing a proven mechanism can fix an unrelated problem for free | Confirmed (2026-08-23) | Entry 22 already established (and verified against SDK source) that `stdio_client`-spawned subprocesses only inherit a small, fixed OS-level env allowlist — never the parent process's real environment. Routing `execute_command` through that *same* gated-tool stdio path (needed anyway, for Entry 30's fix) closed a second, unrelated hole as a side effect: the in-memory `Client` path used for every ungated tool runs inside the live backend process and inherits its *full* environment, so a `python -c "import os;print(os.environ)"` call could have printed `GITHUB_TOKEN` or any other secret straight into the model's context. No new env-scrubbing code was needed — just routing through infrastructure whose security property was already proven. | `llm/agent.py`'s `GATED_TOOLS`/`_call_gated_tool` — `execute_command` added to the same set as `write_file`/`git_commit`/etc., inheriting the same stdio isolation without any new mechanism written for it. |
| 32 | A redaction backstop over source text is inherently approximate, and that's an accepted tradeoff | Confirmed (2026-08-23) | Any regex-based "does this look like a secret" check over arbitrary code text will have false positives (e.g. `access_token = get_token()` isn't a literal secret, but matches the same shape as one) — real secret-scanning tools solve this with entropy analysis, not naive patterns. For a *backstop* layer (the primary defense is blocking known credential filenames outright), occasionally over-redacting ordinary code is a smaller cost than a real secret slipping through un-redacted, and this project already had precedent for accepting an imperfect-but-honest mechanism (Database MCP's statement-shape check is explicitly "a nicer error message," not the real defense; the read-only connection is). | `mcp_servers/security.py`'s `redact_secrets()` — tested and confirmed to correctly redact `GITHUB_TOKEN=`, private key blocks, and credentialed URLs, while *not* flagging bare mentions of "secret"/"token" in filenames or plain identifiers (`test_security.py`'s `test_ordinary_source_files_are_not_flagged`). |
| 33 | A guard on the *input* to a tool isn't the same as a guard on where the tool's *effects* actually land | Learned the hard way, via a second deliberate gap audit (2026-08-23) | `fetch_page`'s SSRF guard checked the URL the caller passed in, but the underlying HTTP client was configured to auto-follow redirects -- so the guard covered the request's starting point, not its actual destination. The same shape of bug appears anywhere a "check once at the boundary" gate sits in front of a mechanism that can itself keep moving (redirects, retries, remote-helper transports) after that single check has already passed. | `fetch_page`'s `follow_redirects=True` let a 302 response silently redirect straight past `_reject_unsafe_url()` to `http://169.254.169.254/...` or DevPilot's own `localhost:8001`; fixed by disabling auto-follow and re-validating every redirect hop through the same guard. |
| 34 | A caller-controlled string in a *positional* argv slot is a different risk than one consumed as a flag's value | Learned the hard way, same audit (2026-08-23) | `git commit -m <message>` and `git branch -d <name>` are safe even with a caller-controlled value, because that value is consumed as the immediately-preceding flag's argument, not re-parsed as its own token. `git push <remote> <branch>` has no such flag in front of `remote`/`branch` -- they're bare positional arguments, so a value starting with `-` risks being read as a flag, and git's own `ext::<command>` remote-helper transport syntax goes further: it isn't argument confusion at all, it's git *intentionally* running `<command>` as a literal shell command when a remote string names that transport. Approval-gating the call doesn't fully cover this, since the approval prompt shows the raw string with no indication it's a transport directive rather than a name. | `git_push(remote="ext::sh -c '...'")` would have made `git push` execute an arbitrary shell command with zero code path through Terminal MCP at all; fixed by rejecting leading `-` and any `x::` substring in `git_push`'s remote/branch and `git_create_branch`/`git_delete_branch`'s name, before the approval prompt is even shown. |
| 35 | Live-testing new code against the real external service beats trusting the documented/assumed response shape | Learned the hard way, third pass (2026-08-23) | GitHub's REST endpoints (repos, contents, commits, pulls) return 403 for an unauthenticated/rate-limited request, and the original `get_repository` (Stage 4) correctly handled that. `search_code`'s endpoint (`/search/code`) turned out to return 401 instead when tested live, unauthenticated, against a real repository -- a detail no amount of re-reading the existing code would have caught, since 401 simply wasn't a case anyone had needed to handle yet. | First implementation of the new GitHub tools shipped with only 404/403 mapped; a live call to `search_code` against `modelcontextprotocol/python-sdk` surfaced a raw, unhelpful `RuntimeError: ... status 401` instead of the intended GITHUB_TOKEN hint -- fixed by mapping 401 the same as 403, confirmed with a second live call. |
| 36 | A fix found for one server is a checklist for every other server with the same shape of tool | Confirmed, fourth pass (2026-08-23) | Git MCP's Entry 42 fix (reject leading `-`/`ext::` in bare positional argv arguments) wasn't actually specific to git -- it was specific to *any tool that passes a caller-controlled string into argv without a preceding flag to consume it*. Docker MCP's `inspect_container`/`get_container_logs`/`stop_container`'s `container`, `run_container`'s `image`, and `build_image`'s `tag` are exactly that shape, and had the same gap, just not yet looked at with that specific lens. Once a vulnerability *class* is identified (not just one instance of it), the right move is to check every tool sharing that shape, not just the one where it was first found. | `mcp_servers/docker/server.py` had zero validation on any of these four caller-controlled identifiers before this pass -- found by deliberately re-reading every subprocess-argv-building tool in the codebase against the "bare positional argument, no preceding flag" pattern, not by a new report. |
| 37 | Plan generation vs. plan execution, closed for real (extends Concept #19) | Confirmed (2026-08-24) | Stage 9 proved *execution* (run a sequence of tool calls, pass results forward, tolerate a step failing) against a hardcoded plan, deliberately deferring *generation* until an LLM existed. An LLM has existed since Entry 17 -- but nothing generated a real plan until now. The design's own worked example (§13: "Plan: 1. Inspect project 2. Run application 3. Capture error...") is a list of plain-language intentions, not a list of pre-computed tool+argument tuples -- matching that shape (rather than the richer `Step{tool, arguments}` structure this entry's own first draft considered) is what makes the plan compatible with adaptive execution afterward. | New "planner" mode: `_generate_plan()` asks the model for an ordered list of step descriptions (JSON array, no tool calls made), shown to the user, held for a whole-plan approval, then folded into the existing tool-calling loop as guidance for real execution. |
| 38 | A structured "preview" step and an adaptive execution loop are not in tension -- they compose | Confirmed (2026-08-24) | The tempting design was a dedicated step-executor: for each planned step, look up its tool+arguments and run it in sequence. That fails the moment a later step's real arguments depend on an earlier step's actual output (a specific test name from real test output, a real file path found by searching) -- which is exactly the case in the design doc's own Debug-FastAPI workflow. The chosen design instead treats the plan as *guidance* injected into the same message-based loop every other mode already uses: the model still decides each real tool call as results come in, but now against a plan the human has already seen and approved, and can explain deviations from it in its own answer text. | `ask()`'s planner branch fixes up `user_message` (prefixing the approved plan) and `mode` (falls through to `"agent"`'s full tool access) once approved, then runs the identical iteration loop below -- no separate step-execution code was written at all. |
| 39 | A whole-plan approval and a per-tool-call approval are different granularities of the same idea, not competing mechanisms | Confirmed (2026-08-24) | Approving a plan upfront ("yes, investigate and fix this") doesn't -- and shouldn't -- pre-authorize every individual mutating action the plan might turn out to need; each `write_file`/`git_commit`/etc. GATED_TOOLS call encountered while carrying out an approved plan still pauses for its own separate approval, exactly as it would in Agent mode. The two layers stack rather than substitute for each other. | `AgentSession` gained a second, independent pause point (`pending_plan`/status `"awaiting_plan_approval"`) alongside the existing `pending`/`"awaiting_approval"` -- both can occur in the same turn, in sequence, for the same underlying reason (a human decision the server can't make alone), at two different scopes. |
| 40 | A real tool schema, inlined into a chat template, is a lot bigger than it looks | Learned the hard way, measured directly (2026-08-27) | The fine-tune's original plan specified `max_seq_len: 2048`. Measured against the real Qwen2.5-Coder-1.5B-Instruct tokenizer and DevPilot's real 33-tool Agent-mode schema, the *prompt alone* — before any completion is added — renders to roughly 3,850 tokens, because the chat template inlines every offered tool's full JSON schema (name, description, parameters) into the system message. At 2048, 14 of 33 real Phase-1 examples (every Plan/Agent-mode one) were silently dropped as "too long," which would have quietly gutted the dataset's coverage of exactly the modes that matter most. | `ml/train/format_example.py`'s `max_seq_len` default raised 2048 -> 4096, verified (not assumed) to cover the full real dataset with headroom: 51/51 examples fit, longest real sequence measured at 3,867 tokens. |
| 41 | Completion-only masking can be verified structurally, not just assumed correct | Confirmed against the real base-model tokenizer (2026-08-27) | TRL's usual approach (`DataCollatorForCompletionOnlyLM`) finds the prompt/completion boundary by string-matching a response template against the *tokenized* sequence -- a well-documented source of silent off-by-one bugs when a chat template's special tokens don't retokenize identically in every context. Downloading the real tokenizer (no GPU needed for this, only for training itself) made it possible to directly verify a stronger property instead of assuming one: `apply_chat_template(prompt_messages, add_generation_prompt=True)` is an exact *string prefix* of `apply_chat_template(prompt_messages + [assistant_message])`, for both a tool-call completion and a plain-text one. That prefix property means the prompt/completion boundary can be computed once, exactly, from real tokenization -- not inferred from string-matching after the fact. | `ml/train/format_example.py`'s `Tokenized` labels: everything before the verified prompt-token boundary is set to `-100` (PyTorch's ignore-index for cross-entropy loss); confirmed via `tests/test_format_example.py` decoding the unmasked label span back to text and checking it's exactly the real tool call (or refusal text) and nothing from the prompt. |
| 42 | A rate metric's denominator has to match what the metric can actually measure | Learned the hard way, via a failing test (2026-08-28) | `exact_tool_match` structurally can't be true for a refusal-expected example (there's no tool to match against), and `mode_violation` structurally can't be true for a tool-call-expected example. Averaging either over a dataset that mixes both example types dilutes the reported rate in a way that's actively misleading, not just imprecise -- a test asserting a perfect predictor should score 100% got 67% instead, purely because 1 of its 3 fabricated examples was refusal-type. The fix (score each rate only over its own relevant subset) mirrors a pattern this project had already used for `argument_f1` (returns `None`, not `0.0`, when there's nothing comparable) -- the same principle, just not yet applied to the other two rates until a test caught the gap. | `ml/eval/harness.py`'s `evaluate()`: `exact_tool_match_rate` computed only over `expected_type == "tool_call"` results, `mode_violation_rate` only over `expected_type == "refusal"` results; `schema_valid_rate`/`task_completion_rate` correctly stay over the full set, since both are meaningful for every example type. |
| 43 | A general-purpose model's real failure rate on a specific app's own rules is measurable, not just plausible | Confirmed live against the real base model (2026-08-28) | The whole fine-tune project rests on a claim -- "the general Ollama model was never trained on DevPilot's mode-restriction logic, so it should fail at respecting it sometimes" -- that had never actually been measured before this. Running the real eval harness against the real live `qwen2.5:7b-instruct` on the real 18-example held-out set turned that claim into a number: it called a tool anyway on 37.5% of the refusal-expected examples (Plan/Ask-mode requests needing a tool outside what's allowed). That's the actual, quantified gap the fine-tune is trying to close -- not assumed, measured. | `ml/eval/out/ollama_report.json` (gitignored, regenerated per run): `mode_violation_rate=0.375`, `schema_valid_rate=1.0` (every tool call it did make was well-formed), `task_completion_rate=0.611`, `p50=20.6s`/`p95=150.4s` latency on this CPU-only hardware. |
| 44 | A fine-tune winning on one axis and losing on another, on the same real run, is a more credible result than uniform wins -- and often traces to one identifiable cause | Confirmed live, both models on the real held-out set (2026-08-28) | The fine-tuned 1.5B model hit `mode_violation_rate=0%` (down from the base 7.6B model's 37.5%) -- the exact thing this project set out to fix, genuinely won. In the same run, `exact_tool_match_rate` dropped to 0% (from the base model's 50%, on the same 2 `list_directory` tool-call examples both models were asked).
