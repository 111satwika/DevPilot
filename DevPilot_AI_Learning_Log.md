# DevPilot AI – Concepts, Approach & Implementation Log

This file is the running record for the DevPilot AI build. It exists so
that at any point — mid-project or months later — you (or I) can answer
"what have we actually covered, decided, and built" without re-reading
the whole conversation history.

It has three parts, updated in this order as we go:

1. **Concepts Learned** — MCP/AI concepts once they've been explained.
2. **Approach & Decisions** — architecture/process choices and *why*.
3. **Implementation Log** — what's actually been built and tested.

Nothing gets added to a section until it's actually happened — this is
a log, not a plan. The plan lives in `DevPilot_AI_MCP_Project_Design.md`.

# 1. Concepts Learned

| # | Concept | Status | Summary | DevPilot context |
|---|---------|--------|---------|-------------------|
| 1 | What is MCP | Introduced (2026-08-09) | A standard client-server protocol so any LLM app can talk to any tool/data source without bespoke glue code (N×M → N+M integrations). | Why DevPilot's 7 capabilities can be built as independent, swappable MCP servers instead of one tangled program. |
| 2 | MCP Client vs MCP Server | Introduced (2026-08-09) | Client lives in the app and talks to servers over a transport; each server exposes one capability's tools. | MCP Client = DevPilot's orchestration layer; Filesystem/Terminal/GitHub/etc. = separate servers. |
| 3 | Tool discovery | Introduced (2026-08-09) | Client asks a server "what tools do you have?"; server replies with name + description + JSON input schema per tool. | How the LLM learns what `filesystem.read_file` even is, before ever calling it. |
| 4 | Tool invocation | Introduced (2026-08-09) | Client sends a tool name + arguments to the server; server executes and returns a result, which flows back to the LLM as context. | The `read_file` → result → LLM step in every DevPilot workflow. |
| 5 | `content` vs `structured_content` | Learned the hard way (2026-08-09) | Every tool result carries both: `content` is display-oriented text blocks, `structured_content` is the real typed return value. A `list`-returning tool splits across N `content` blocks (full value only in `structured_content`); a `dict`-returning tool puts everything in one `content` block and leaves `structured_content` as `None`. Not interchangeable — assuming `content[0].text` is "the answer" silently truncates list results. | Caught via a real bug in `stage2_client.py`: `list_directory` appeared to return 1 entry instead of 8. |
| 6 | Tool schema (detail) | Reinforced (2026-08-09) | Auto-generated from type hints; the Python SDK object exposes it as `tool.input_schema` (snake_case), which differs from the wire protocol's `inputSchema` field name. | Caught via `AttributeError` in `stage2_client.py` — SDK attribute names and wire field names aren't guaranteed to match. |
| 7 | Tool Permissions (allow-listing) | Introduced (2026-08-10) | A tool doesn't have to accept everything it's technically capable of — `execute_command` rejects any binary not in a fixed allow-list *before* spawning a process, no execution attempt at all. | Terminal MCP's whole security model for Stage 3: `rm` is refused outright rather than run-and-caught. |
| 8 | Error Handling: tool failure vs. task failure | Introduced (2026-08-10) | A command that runs and exits non-zero is a **successful tool call** reporting a failure (`is_error` stays false) — not the same thing as the tool itself erroring (bad input, disallowed command, timeout), which *does* set `is_error`. | `execute_command` running `python -c "sys.exit(1)"` returned `exit_code: 1` as normal `structured_content`, no MCP-level error. |
| 9 | Multi-server architecture | Introduced (2026-08-10) | Independent MCP servers share no state and don't know about each other — GitHub MCP has no awareness of Filesystem/Terminal MCP. The client is the only thing that ever combines what several servers know. | First server (GitHub) with zero overlap in concerns with the other two — no sandboxing, no allow-list, entirely new failure modes (network/HTTP) instead. |
| 10 | Secrets handling in a tool | Introduced (2026-08-10) | A credential (`GITHUB_TOKEN`) is read only from the environment inside the tool, never accepted as a tool parameter and never returned in output — so there's no code path where the LLM could pass, see, or leak it. | `get_repository`'s schema exposes only `owner`/`repo`; confirmed via `list_tools()` that no token-shaped field exists. |
| 11 | External knowledge retrieval (vs. RAG) | Introduced (2026-08-10) | Grounding an LLM's answer in real external content doesn't require the full RAG pipeline (chunking/embeddings/vector DB) — "search, fetch, read the text" is a complete, useful capability on its own. RAG is a later, separate addition, not a prerequisite. | `search_web` + `fetch_page` give DevPilot real documentation lookup with zero retrieval infrastructure. |
| 12 | SSRF (Server-Side Request Forgery) | Introduced (2026-08-10) | A "fetch any URL" tool is a classic SSRF vector — it can be pointed at internal services (`localhost`, private IPs) or cloud metadata endpoints (`169.254.169.254`) that were never meant to be reachable this way. Guarding against it means checking both the hostname *and* the IP it resolves to, before fetching. | `fetch_page`'s `_reject_unsafe_url()`, tested against both a hostname (`localhost`) and an IP-literal (`169.254.169.254`) attack shape. |
| 13 | Mechanism over pattern-matching (structural defense) | Reinforced (2026-08-10) | Preferring a mechanism that makes the dangerous action *impossible* over one that tries to detect and block it after the fact. First seen in Stage 3 (`shell=False` — no shell means no metacharacters to blocklist); reinforced in Stage 6 with a genuinely independent test. | Opened SQLite in read-only mode (`file:...?mode=ro`); a raw write attempted *directly against that connection, bypassing the tool's own prefix check entirely*, still failed with `sqlite3.OperationalError: attempt to write a readonly database` — proving the engine-level guarantee, not just the string check in front of it. |
| 14 | Human-in-the-loop / MCP elicitation | Confirmed working end-to-end (2026-08-10) | A tool can pause *mid-execution* and ask the connected client/user a question via `ctx.elicit(message, schema)`, then resume based on `AcceptedElicitation`/`DeclinedElicitation`/`CancelledElicitation`. This is a fundamentally different safety mechanism from every prior gate — sandboxing/allow-listing/SSRF-checks/read-only-connections are the *server* deciding alone; elicitation makes the *human* the gate, and the server literally cannot decide by itself. | `write_file` on Filesystem MCP (Stage 8) — the first tool the server can't resolve on its own. Approve/decline paths both confirmed with independent `read_file` checks, not just trusting the write call's own report. |
| 15 | Fail-safe defaults | Confirmed (2026-08-10) | When no `elicitation_callback` is registered on the client, MCP's own default handler refuses the request rather than silently approving or hanging — absence of an approval mechanism means *nothing* gets approved, not everything. | Tested directly: a bare `ClientSession` with no callback made `write_file` fail, and a follow-up `read_file` confirmed no file was created — "fails safe" verified as "nothing written," not just "an error appeared." |
| 16 | Server-initiated requests need a real back-channel | Learned the hard way (2026-08-10) | The in-memory `Client(mcp)` shortcut (used since Stage 1) is a direct function call dressed as a client/server relationship — it has no channel for the *server* to send a request *to* the client mid-call. Elicitation needs exactly that. Any MCP capability requiring server→client requests (elicitation, sampling, roots) needs a real transport, full stop. | `NoBackChannelError` on the first Stage 8 attempt forced a switch to real `StdioServerParameters`/`stdio_client`/`ClientSession` — the first genuinely separate-process connection in the project, arrived at by necessity rather than by plan. Retroactively corrects the Entry 4 decision. |
| 17 | Protocol-level errors vs. tool-level errors | Learned the hard way (2026-08-10) | Not every failure comes back as `CallToolResult(is_error=True)`. A missing elicitation callback fails at the *protocol* level — `MCPError` raised straight out of `call_tool()` (wrapped in an `ExceptionGroup` by anyio's structured concurrency, needing Python 3.11+'s `except*` to catch) — structurally different from every other error this project has produced (allow-list/sandbox/SSRF rejections, declined approvals), which all surface as ordinary tool results. | First `except MCPError` attempt in `stage8_client.py` silently failed to catch anything; `except* MCPError` was needed. |
| 18 | Multi-server orchestration in one client | Confirmed working (2026-08-10) | Every client through Stage 8 connects to exactly one server. A planner/orchestrator is the first client that talks to *two* servers in the same script, in sequence, using each step's result independently of how the others turned out. This — not cleverness in choosing steps — is the real mechanical substance of "planning." | `planner.py` calling Terminal MCP twice and Filesystem MCP once in a single run, producing one combined report. |
| 19 | Plan generation vs. plan execution | Introduced (2026-08-10) | These are separable concerns: *execution* (run a sequence of tool calls across servers, pass results forward, tolerate individual failures) doesn't require an LLM at all; *generation* (turning a free-text request into that sequence) does. Proving execution first, with a fixed hand-written plan, isolates "MCP mechanics" from "LLM plumbing" instead of conflating them in one stage. | Stage 9 ships execution only; `PLAN` in `planner.py` is a hardcoded Python list, not LLM output. |
| 20 | Session vs. project memory (lifetime) | Confirmed working across 2 real processes (2026-08-10) | Session/conversation memory dies with the process; project memory persists across separate runs. The difference is only real if demonstrated across an actual process boundary, not just two calls inside one script. | `planner.py` run twice as genuinely separate OS processes: `ProjectMemory`'s `stages_completed` read back as 1 in run 2 (written by run 1) and became 2; every `SessionMemory.summary()` in both runs started from zero entries regardless. |
| 21 | Cross-environment execution (Windows host, WSL-bridged tool) | Introduced (2026-08-11) | An MCP server doesn't have to run its underlying capability in the same OS environment as the Python process hosting it — as long as there's a reliable bridge (here, `wsl.exe`) and a way to translate paths between the two environments' filesystems, the tool abstraction still holds. | Docker MCP's Windows Python process calls `docker` (which only exists in WSL) via `wsl -d Ubuntu -e docker ...`, with `_to_wsl_path()` converting the sandboxed Windows path into WSL's `/mnt/<drive>/...` mount for `build_image`. |
| 22 | Defense-in-depth vs. reachable gate | Introduced (2026-08-11) | Not every safety check sits on a path a caller can actually reach. Docker MCP's subcommand allow-list guards against a *future* tool that might expose a free subcommand parameter — none of today's six tools do, each hardcodes its own subcommand — so it's defense-in-depth, not the primary gate the way Terminal MCP's identical-looking allow-list is (where `command` genuinely is caller-controlled). | Had to be tested by importing `_run_docker()` directly, since no tool call could reach the rejection path through the public API. |
| 23 | Approval vs. underlying success are independent | Confirmed (2026-08-11) | "Was this approved?" and "did the approved action succeed?" are two separate questions. `git_commit`'s approve-path correctly reached real git execution and got a real git error (not a git repo) — proving the approval → execution wiring works, without needing the underlying operation to actually succeed. | `git_commit`, approved, in a folder with no `.git` — `AcceptedElicitation` was returned, `_run_git()` was genuinely called, and it failed for an honest, unrelated reason. |
| 24 | First LLM in the loop | Confirmed working (2026-08-11) | The actual "AI" in DevPilot AI — 6 servers, 26 tools, and a memory system were all built and tested before any of them had a model to sit under. A model with no project context honestly said "I don't know" rather than inventing a plausible-sounding answer, which is precisely the gap MCP tool access (Piece 2) exists to close. | `llm/demo.py` asking a local model to name an MCP server this project built — it correctly declined to guess. |
| 25 | Tool selection vs. answer synthesis are separate capabilities | Learned the hard way, twice (2026-08-11) | An LLM correctly discovering, choosing, and chaining the right tools across multiple servers does not guarantee it correctly synthesizes a final answer from everything it gathered. These are two different failure points and need testing separately. | Run 2 of the agent test: model called `read_file` (Filesystem) then `list_tables`/`describe_table` (Database) — genuine cross-server chaining, entirely correct — then wrote a final answer that silently dropped the dependency data it had already fetched. |
| 26 | A tool list is a real security/scope boundary, not just a convenience | Learned the hard way (2026-08-11) | "Which server object I import and pass to `list_tools()`" determines exactly which capabilities an LLM can reach — including ones never intended to be exposed. Importing a whole MCP server pulls in everything registered on it, approval-gated tools included, unless explicitly filtered. | `write_file` (Stage 8's approval-gated tool) appeared in the LLM's tool list on the first run despite the Approach explicitly scoping this piece to read-only tools — caught by testing, not by re-reading the plan. |
| 27 | System prompts as a coverage lever | Confirmed working (2026-08-11) | An explicit "check your answer covers every part of the question before finalizing" instruction in a system-role message fixed Entry 18's synthesis gap on the first re-run of the identical question — a prompting mitigation, not a structural guarantee, and reported as exactly that. | Same two-part question as Entry 18 Run 2: with the system prompt, the model gathered both facts in one turn and produced a complete, accurate two-part answer; without it, it had dropped one part twice. |
| 28 | HTTP surface doesn't change the underlying pipeline | Confirmed (2026-08-11) | Wrapping `llm/agent.py`'s `ask()` in a FastAPI endpoint and calling it over real HTTP produced the same correct behavior as calling it directly from a Python script — the MCP discovery/selection/execution/synthesis pipeline is transport-agnostic, as it should be, and this was verified rather than assumed. | `POST /ask` on a real running `uvicorn` server returned the correct answer about the demo database's tables, matching prior in-process test results. |

Also reinforced: `subprocess.run([...], shell=False)` passes command+args as a list, so shell metacharacters (`;`, `&&`, `|`) never get shell-parsed in the first place — simpler and stricter than blocklisting dangerous characters in a string.

# 2. Approach & Decisions

| Date | Decision | Why |
|------|----------|-----|
| 2026-08-09 | Teaching method: no code dumps. For every concept — explain → smallest working example → test it → explain what happened → only then move on. | User is learning MCP, not just shipping a project; source of truth is `# DevPilot AI – MCP Learning & Build Ins.md`. |
| 2026-08-09 | Server class is `MCPServer` from `mcp.server` (not `FastMCP`, which is what older tutorials/training data reference). `@mcp.tool()` decorator and `mcp.run()` are unchanged in spirit. | Verified directly against the `modelcontextprotocol/python-sdk` source on GitHub (`src/mcp/server/mcpserver/server.py`) since the SDK moves fast and stale API knowledge would break the first example. |
| 2026-08-09 | Lesson 1's smallest example uses `mcp.Client(server)` for an **in-memory** connection, not a subprocess over stdio (`stdio_client`/`ClientSession`). | Matches the current official SDK quickstart; keeps the first example focused on Client/Server/Tool/Invocation without also introducing transport mechanics. Real subprocess transport (`StdioServerParameters`, `stdio_client`, `ClientSession`) is confirmed available and deferred to the dedicated MCP Transport lesson. |
| 2026-08-09 | Filesystem/Terminal sandboxing (workspace-root boundary, command allow-list) is built into **Phase 1**, not deferred to a later hardening pass. | These two servers are unsafe by default the moment they exist; retrofitting security is how real incidents happen. |
| 2026-08-09 | Redis, Arq (job queue), and observability tooling (structlog, prometheus-client) are introduced in Phase 3/4, not provisioned upfront. | Avoids overengineering a Phase 1 that's still just "learn the base protocol"; matches the project's own "avoid overengineering" instruction. |
| 2026-08-09 | Each build phase is explicitly mapped to the MCP concepts it exercises (see `DevPilot_AI_MCP_Project_Design.md` → How to Build). | So building the project *is* the mechanism for learning MCP concepts in order, per the learning objective list. |
| 2026-08-09 | Before writing any MCP-specific code, verify current official SDK API/syntax rather than relying on possibly-outdated memory. | Explicit requirement in the build-instructions file; MCP SDK is young and has moved fast. |
| 2026-08-10 | GitHub MCP uses `httpx2` (already installed as a transitive dependency of `mcp`), not the classic `httpx` package. | Checked by direct import in `.venv` rather than assumed — `import httpx` fails, `import httpx2` works and exposes the same API shape (`Client`, `HTTPStatusError`, etc.). Avoids adding a redundant HTTP dependency. |
| 2026-08-10 | GitHub MCP's auth token is read only from the `GITHUB_TOKEN` env var, never accepted as a tool parameter, never included in any tool's return value. | Same secrets-handling principle from the production-considerations section, now applied to the first server with real credentials involved. |
| 2026-08-10 | Browser MCP's `search_web` scrapes DuckDuckGo's public HTML endpoint (no API key) rather than a paid search API. | Zero-cost for a learning project; deliberately flagged as a stopgap with a known weakness (no markup-change guarantee) — tool signature (`query -> list[dict]`) is designed to survive swapping in a real search API later without changing callers. |
| 2026-08-10 | Browser MCP's `fetch_page` rejects non-http(s) schemes and internal/private/loopback hosts before fetching. | SSRF is the real risk for a "fetch any URL" tool, not sandboxing (there's no workspace-style boundary to apply when the point of the tool is reaching external URLs) — same "security from day one" precedent as Filesystem/Terminal, applied to a different threat shape. |
| 2026-08-10 | Database MCP uses SQLite, not PostgreSQL as the build-instructions file specifies. User-confirmed after checking: no `psql`, nothing on `localhost:5432` in this environment. | Every prior stage was tested against something real; writing untested Postgres code would break that pattern. Tool signatures kept engine-agnostic so a later Postgres swap only touches the connection layer. |
| 2026-08-10 | `execute_read_query` opens the SQLite connection itself in read-only mode (`file:...?mode=ro`), not just a keyword blocklist on the query text. | Same insight as Stage 3's `shell=False`: a mechanism that makes writes structurally impossible beats pattern-matching to block them after the fact. The statement-shape check (must start with SELECT/WITH) stays too, but only as a nicer error message — the read-only connection is the real defense. |
| 2026-08-10 | Dropped `list_databases` from the planned tool set (build-instructions file lists 4 tools, Stage 6 ships 3). | Postgres-specific concept — one server hosts many databases. A SQLite connection already points at exactly one file; there's nothing for the tool to list. |
| 2026-08-10 | Stage 7 (Docker MCP) deferred entirely, user-confirmed. No `docker` CLI found in this environment at all (not just a stopped daemon). | Unlike Stage 6's Postgres→SQLite swap, there's no lightweight stand-in for a container runtime that would keep the stage genuinely testable — proceeding to Stage 8 instead. |
| 2026-08-10 | Approval workflow (Stage 8) uses MCP's native **elicitation** mechanism (`ctx.elicit()`), not a hand-rolled approval queue. | It's the protocol's actual built-in answer to "pause a tool call and ask the human something" — verified by reading the real SDK source (`tools/base.py`, `context.py`, `mcp/server/elicitation.py`, `client/session.py`) rather than assumed. |
| 2026-08-10 | Only one tool gated behind approval for Stage 8: a new `write_file` on Filesystem MCP. | The build-instructions file has said since §6 that file-modification tools need approval, and every write op deferred so far pointed at "once Stage 8 exists" — proving the mechanism once, correctly, matters more than rolling it out to every server immediately. |
| 2026-08-10 | Stage 8's test client switched from the in-memory `Client(mcp)` pattern to real `StdioServerParameters`/`stdio_client`/`ClientSession`, correcting the Entry 4 decision. | Forced by `NoBackChannelError`, not planned — the in-memory shortcut has no channel for server-initiated requests, which elicitation requires. First genuinely separate-process MCP connection in the project. |
| 2026-08-10 | Stage 9's planner uses a fixed, hand-written plan, not an LLM-generated one. | No LLM integration exists in this project yet (no API key handling, no prompt/response loop built at all) — generating that plan needs it. Proves the execution half (multi-server orchestration, context passing) now; plan *generation* is deferred until LLM integration exists, consistent with every prior scope deferral. |
| 2026-08-10 | Stage 9's step 4 ("combine results into a report") is plain string formatting, explicitly not called a "summary" implying LLM reasoning. | Honest framing — with no LLM wired in, claiming synthesis would overclaim what the code does. |
| 2026-08-10 | Stage 10's memory lives entirely client-side (`mcp_client/memory.py`) — no new MCP server or tool. | Memory is the orchestrator's own state, not a capability meant to be discovered/invoked externally; the build-instructions file discusses it alongside planning/tool-selection, not the server sections. Keeps the client/server distinction sharp. |
| 2026-08-10 | Project memory is a plain JSON file, not a new table in the Database MCP's SQLite file. | Tempting (would extend Stage 8's approval-gated-write pattern to a 2nd server) but explicitly against this stage's own "do NOT introduce complicated ... initially" instruction — a JSON file is the smallest thing that proves real persistence. |
| 2026-08-10 | Stage 7 (Docker MCP) revisited and built despite Docker still not being installed here (re-confirmed). | User-directed. Reframed rather than blindly proceeding: precisely separated what's testable without Docker (allow-list, sandbox, approval flow, graceful "not installed" handling) from what isn't (real container behavior) — "not installed" is treated as a real scenario to handle well, not a gap to apologize for. |
| 2026-08-10 | Docker MCP reuses three already-built mechanisms rather than inventing new ones: Terminal's allow-list+argv pattern, Filesystem's workspace-sandbox for build context, Stage 8's elicitation for the three state-changing tools. | Docker MCP is the most powerful/dangerous server in the architecture — reusing already-tested safety logic beats designing new logic for the highest-stakes server under the constraint of not being able to test against a real daemon. |
| 2026-08-11 | Docker turned out to be installed inside WSL2 Ubuntu (Docker Engine via `apt`, not Docker Desktop) — not on Windows PATH at all. Every docker call is bridged through `wsl -d Ubuntu -e docker ...`, verified working from the actual `.venv` Python subprocess path before any server code was written. | DevPilot's MCP servers run as Windows Python processes; Docker only exists inside the WSL environment. Confirmed by testing directly (`subprocess.run(['wsl', ...])`) rather than assumed. |
| 2026-08-11 | `build_image` translates the Windows-side sandboxed path to WSL's auto-mounted `/mnt/<drive>/...` equivalent before passing it to `docker build`. | The sandbox check itself stays Windows-side (reusing the Filesystem pattern), but the actual `docker` process runs inside WSL and needs a Linux-style path — two different path spaces need bridging, not just one subprocess call. |
| 2026-08-11 | **Discrepancy found, not caught in the moment**: the design doc lists 7 MCP servers (incl. Git); the build-instructions file's own Stage sequence only ever specifies 6, folding git into Terminal's allow-list instead. Every server built through Entry 15 followed the build-instructions Stage list, silently inheriting this gap. | Unlike every other deviation in this project (all flagged live), this one surfaced only when asked directly — worth recording as a real gap in review diligence, not a considered trade-off. |
| 2026-08-11 | Decision: build a dedicated Git MCP server (user chose this over updating the design doc to match 6 servers). Scope taken directly from build-instructions §19 ("Git security"): approval required before commit, push, branch deletion — nothing else invented. | Closes the gap toward the original 7-server design rather than redefining the design down to match what was already built. |
| 2026-08-11 | LLM provider switched from Anthropic Claude to local Ollama (`qwen2.5:7b-instruct`), after confirming no Anthropic credentials exist here and the user confirmed Claude API billing is separate from their Claude Code subscription. | User explicitly required zero cost, stated twice. Ollama was already running in this environment (discovered via Docker MCP exploration) and confirmed to support tool-calling via its own capabilities field — not assumed from the model name. |
| 2026-08-11 | Ollama calls are bridged through `wsl -d Ubuntu -e curl ...` with the JSON body passed via stdin (`-d @-`), not as a command-line argument. | Same cross-environment shape as Docker MCP (only reachable from WSL, confirmed by testing a direct Windows call and getting a timeout) — stdin avoids cross-shell argument-escaping bugs, the same class of reasoning behind every `shell=False`/argv-list choice in this project, applied to a new failure mode. |
| 2026-08-11 | The Ollama container's bridge IP is resolved fresh via `docker inspect` on every call rather than hardcoded. | Docker bridge IPs aren't stable across container restarts — a value observed once isn't safe to freeze, the same lesson as the Docker MCP entry. |
| 2026-08-11 | Piece 2 (dynamic tool selection) exposes only 7 read-only tools from Filesystem + Database MCP — no approval-gated tools yet. | Routing an LLM's own tool choice through human approval is a separate, harder problem (who answers the prompt?) deserving its own piece, not bundled into "does dynamic selection work at all." Read-only also means the in-memory transport stays valid, same reasoning as Stage 9. |
| 2026-08-11 | Ollama's real per-call latency (50–57s observed) is treated as a real design constraint (timeouts, iteration caps, test-runtime expectations), not glossed over. | Honest trade-off of the zero-cost decision from Entry 17 — free and slow is the actual deal being made, not free and equivalent. |
| 2026-08-11 | The answer-synthesis gap (Entry 18) is addressed with one system prompt, tried once, not a retry loop or code-level checklisting logic. | Prompting is the smallest lever available; a structural fix (forced sub-question tracking) is real added complexity that isn't justified until a single honest prompt-level attempt is shown not to work. |
| 2026-08-11 | The FastAPI backend (`backend/main.py`) is a plain synchronous blocking endpoint with a generous timeout, not a job queue, despite multi-minute agent calls. | Same "not justified until it's a real problem" reasoning as Terminal's timeout and Docker's build timeout — a job queue is real infrastructure the design doc itself flags as a later concern, not a day-one requirement. |
| 2026-08-11 | `backend/` created as a real top-level package now, resolving the deferral logged in Entry 17 (`llm/` was kept flat because `backend/` didn't exist yet). | The backend is genuinely being built now — creating the nesting earlier would have been scaffolding for a thing that didn't exist. |
